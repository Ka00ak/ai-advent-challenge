# 10. Архитектурные решения, риски, открытые вопросы

## ADR-1. Три слоя, summary — атрибут STM

**Контекст:** ТЗ требует минимум три типа памяти. В Дне 10 summary был
отдельной стратегией, facts — отдельной памятью.

**Решение:** ровно три слоя: STM, WM, LTM. Сводка вытесненных сообщений — часть
STM, а не четвёртый слой. LTM наследует facts Дня 10.

**Следствия:** простая модель для UI и эксперимента; summary не участвует в
ablation отдельно; при желании её можно выключить в настройках STM.

## ADR-2. Раздельные ключи localStorage

**Контекст:** можно хранить всю память одним JSON-снимком.

**Решение:** отдельный ключ на слой (`conversation/summary`, `working`, `ltm`,
`pending`, `meta`). Версия и валидатор — у каждого ключа.

**Следствия:** сбой одного слоя не ломает другие; очистка слоя тривиальна;
чуть больше кода на чтение/запись; миграции проще.

## ADR-3. Local-first извлечение, LLM — опция

**Контекст:** LLM-извлечение точнее, но стоит запрос на каждую реплику.

**Решение:** по умолчанию `local` (эвристика Дня 10 + маркеры задачи). `llm` —
переключатель; при ошибке откат на `local`.

**Следствия:** демо работает без ключа и без лишних затрат; свободные
формулировки могут теряться; это явно описано в ограничениях.

## ADR-4. LTM подтверждается по умолчанию

**Контекст:** требование «явно выбирать, что и куда сохраняется».

**Решение:** `approval = 'confirm'`: WM пишется сразу, LTM — через очередь
pending. `auto` доступен, но не по умолчанию. Ручные действия всегда явные.

**Следствия:** пользователь контролирует долговременную память; появляется
очередь и её хранение; без подтверждения LTM не растёт.

## ADR-5. Лексический retrieval вместо embeddings

**Контекст:** векторный поиск дал бы семантику, но требует модель, индекс и
деньги.

**Решение:** score по key/tags/value + pinned + confidence + свежесть, top-K,
бюджет. Детерминированно и тестируемо.

**Следствия:** синонимы могут не находится; компенсируется тегами, `pinned`,
ручным поиском и LLM-извлечением с нормальными ключами. Векторный поиск — P2.

## ADR-6. Промпт собирается один раз за запуск

**Контекст:** `memory_write` может вызваться в середине tool-loop.

**Решение:** блоки памяти собираются перед первым запросом. Запись через tool
подтверждается в ответе инструмента, но в промпт текущего запуска не
подмешивается; она влияет со следующего хода пользователя.

**Следствия:** стабильный префикс, простая отладка, нет рассинхрона; агент
узнаёт о своей записи из результата tool. Компромисс осознанный.

## ADR-7. Отдельное system-сообщение на блок

**Контекст:** можно склеить все блоки в один system.

**Решение:** каждый блок — отдельное system-сообщение; при несовместимости
провайдера — склейка в том же порядке с сохранением разбивки токенов.

**Следствия:** прозрачный журнал и токены по слоям; некоторые провайдеры
требуют один system — предусмотрен fallback.

## ADR-8. Миграция facts идемпотентна

**Контекст:** facts Дня 10 — основа LTM, но пользователь может импортировать
их повторно.

**Решение:** upsert по `key`; совпадающее значение → skip; изменённое →
обновление; `legacyKey` и тег `migrated:day10` сохраняются.

**Следствия:** повторный импорт безопасен; старые ключи остаются в `lab10.*`
как источник, но не читаются в рантайме.

## ADR-9. Эксперимент: детерминированная фикстура + keyword scoring

**Контекст:** нужны воспроизводимые результаты без второй модели-судьи.

**Решение:** 34 сообщения и 18 probe фиксированы; ответ оценивается по
ключевым словам; `temperature = 0`; сводка STM выключена в ablation. Реальный
прогон — вручную, отчёт сохраняется.

**Следствия:** результаты сравнимы между запусками; семантические синонимы
могут не засчитаться; это отмечено в ограничениях. Автотесты на моке проверяют
механику, не качество модели.

## ADR-10. WM живёт в localStorage, а не только в сессии

**Контекст:** рабочая память логически привязана к задаче, но пользователь
может закрыть вкладку.

**Решение:** WM сохраняется в `lab11.working.v1`, привязана к `taskId`;
очищается вручную или при «Завершить задачу»/GC.

**Следствия:** задача переживает перезагрузку; нужно следить за устареванием
(`ttlDays`) и не путать с STM.

## ADR-11. Ветки — снимок всех слоёв

**Контекст:** в Дне 10 ветки хранили messages + summary + facts.

**Решение:** снимок включает STM, WM, LTM, pending, meta; переключение
заменяет всё целиком.

**Следствия:** ветки остаются согласованными с новой моделью; размер снимка
растёт, нужен лимит и предупреждение.

## ADR-12. Переключатель стратегий удаляется

**Контекст:** День 10 предлагал выбрать одну стратегию; День 11 использует все
слои одновременно.

**Решение:** `contextStrategy` удаляется; вместо него — панель слоёв и ablation
в эксперименте. `sliding` соответствует `stm`-конфигурации, `facts` — LTM+WM,
`summary` — STM со сводкой.

**Следствия:** UI проще; старые настройки мигрируют; старый benchmark остаётся
только как референс в коде/тестах, если не мешает.

## Риски

| ID | Риск | Вероятность | Влияние | Смягчение |
|---|---|---|---|---|
| R-1 | Retrieval не находит нужную LTM-запись | средняя | высокое | теги, pinned, top-K, ручной поиск, LLM-извлечение |
| R-2 | Дублирование между WM и LTM | высокая | среднее | `refLtmId`, dedupe, `shadowed-by-wm`, правила R2/R3 |
| R-3 | Бюджет усекает важное | средняя | высокое | приоритеты, pinned, `notes`, индикатор в UI |
| R-4 | Фикстура «подсказывает» чужие ответы | средняя | высокое | тесты изоляции T-F-2…4, сводка выключена |
| R-5 | Эксперимент дорогой/долгий | высокая | среднее | quick-режим, local, отмена, предупреждение |
| R-6 | localStorage переполняется | средняя | среднее | лимиты, GC, предупреждение, экспорт |
| R-7 | Prompt injection через память | низкая | высокое | «данные, не инструкции», санитайзер, лимиты |
| R-8 | Over-engineering | средняя | высокое | P0-срез, запрет vector DB/сервера |
| R-9 | Потеря данных при миграции | низкая | высокое | дословные значения, отчёт, старый ключ не удаляется |
| R-10 | Ветки раздувают storage | средняя | низкое | лимит снимков, предупреждение |
| R-11 | Модель отвечает нестабильно | высокая | среднее | `temperature=0`, keyword scoring, допуск 16/18 |
| R-12 | Расхождение docs и кода | средняя | среднее | T1-контракты, трассировка, ревью перед T14 |

## Открытые вопросы и дефолты

| # | Вопрос | Дефолт для реализации |
|---|---|---|
| Q1 | LTM общая для всех бесед? | Нет, привязана к `conversationId`; глобальный профиль — P2 |
| Q2 | Очистка LTM удаляет pending? | Да, pending относится к LTM |
| Q3 | Маршрутизировать ответы ассистента? | Нет, только user + tool; меньше шума и явнее |
| Q4 | Маршрутизировать импортированную историю? | Нет; курсор начинается с текущего момента, «переиндексировать» — P2 |
| Q5 | Что делать с `superseded` версиями? | Хранить активную + 2 последние |
| Q6 | Можно ли удалить pinned? | Да, но только вручную и с подтверждением |
| Q7 | Сколько живёт pending? | Не удаляется; через 7 дней бейдж `stale` |
| Q8 | Что если провайдер не любит несколько system? | Склеить блоки в один, сохранить breakdown |
| Q9 | Нужен ли summary в полной модели? | Да, по умолчанию; в эксперименте выключен |
| Q10 | Что считать «завершением задачи»? | Кнопка «Завершить задачу» + GC; автоматического продвижения в LTM нет |
| Q11 | Язык ключей LTM? | Латиница, точки: `project.name`, `decision.database` |
| Q12 | Можно ли редактировать значение LTM вручную? | Да, с созданием новой версии и аудитом |

## Что считать провалом дня

- Три слоя есть только на бумаге, а в промпт уходит один общий блок.
- Запись происходит автоматически и бесконтрольно, без pending/аудита.
- Facts Дня 10 не перенесены.
- Нет измерения токенов по слоям.
- Очистка слоёв не проверена или проверена «на глаз».
- Отчёт эксперимента отсутствует или содержит выдуманные числа.
