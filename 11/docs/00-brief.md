# 00. Брифинг и границы

## Контекст

К Дню 11 в репозитории есть День 10 — веб-приложение на Vue/TypeScript с агентом,
инструментами, summary и key-value `facts`. Для Дня 11 **код Дня 10 не
переиспользуется**: новый проект пишется на Kotlin и запускается как TUI.

Из Дня 10 переносятся:

- **facts** (`lab10.facts.v1`) как основа LTM;
- контрольные детали (12 фактов проекта) и идея benchmark;
- понимание проблем: стратегия одна, facts смешивают профиль и разовые детали,
  summary размывает числа, sliding теряет старое.

Браузерный `localStorage` из Kotlin недоступен, поэтому facts импортируются
файлом: экспорт из Дня 10 (кнопка/DevTools) или готовый
`fixtures/day10-facts.json`. Это осознанное изменение формы интеграции, а не
потеря требования.

## Проблема

Нужна **явная модель памяти**, в которой:

1. данные разной природы не конкурируют за одно место;
2. видно, что и почему попало в каждый слой;
3. в промпт уходит ровно нужное и не больше;
4. вклад каждого слоя измеряется в токенах и в ответах;
5. очистка слоя предсказуемо ломает только его вопросы;
6. всё это можно показать в терминале и прогнать headless-командой.

## Цель

Собрать Kotlin-приложение с TUI и CLI, тремя независимыми слоями памяти
(STM, WM, LTM), политикой записи, сборщиком промпта и воспроизводимым
экспериментом.

## Пользовательские сценарии

### С1. Проектный диалог

Пользователь называет проект, заказчика, дедлайн, бюджет и ограничения. После
подтверждения это уходит в LTM. Через 30 реплик агент всё ещё отвечает на
вопросы о проекте, хотя сообщения давно вытеснены из STM.

### С2. Текущая задача

Пользователь ставит задачу «подготовить смету», называет план, варианты, статус
и открытый вопрос. Это WM. Задача завершается — WM очищается, устойчивые
выводы переносятся в LTM только вручную.

### С3. Свежая правка

Пользователь говорит: «бюджет маркетинга подняли до 150 000». Новое значение
сразу видно в STM; в LTM создаётся pending-обновление. До подтверждения агент
отвечает по свежему значению, потому что STM важнее LTM.

### С4. Ревизия памяти в TUI

Пользователь открывает экран «Память», видит три колонки, переносит пункт из
WM в LTM, удаляет устаревшее решение, очищает слой и смотрит, какие вопросы
после этого ломаются.

### С5. Headless-проверка

Агент/CI запускает `experiment --full`, получает Markdown/JSON-отчёт и код
выхода 0/1 по порогам. TUI для этого не нужен.

## Глоссарий

| Термин | Значение |
|---|---|
| **Слой** | независимое хранилище: STM, WM, LTM |
| **Запись** | единица памяти: факт LTM, пункт WM или сообщение STM |
| **Кандидат** | извлечённая из реплики пара «ключ → значение» до маршрутизации |
| **Router** | правила R1–R6, определяющие слой и операцию |
| **Pending** | очередь записей в LTM, ждущих подтверждения |
| **Блок промпта** | отрендеренная часть слоя в системной части запроса |
| **Бюджет** | мягкий лимит токенов на блок |
| **Ablation** | прогон с отключёнными слоями |
| **Probe** | контрольный вопрос с ключевыми словами |
| **Data-dir** | каталог с JSON-файлами слоёв и настроек |
| **TUI** | полноэкранный терминальный интерфейс |
| **CLI** | неинтерактивные команды для автоматизации |
| **Контроллер** | общий слой логики для TUI и CLI |
| **Кадр** | одно обновление экрана TUI |

## Критерии успеха

| # | Критерий | Как проверяем |
|---|---|---|
| K1 | Три слоя физически разделены | разные файлы, разные модули, тесты изоляции |
| K2 | Запись управляемая | аудит: слой, правило, источник; LTM через pending |
| K3 | Facts Дня 10 в LTM | `import-facts` + вопросы L1–L6 |
| K4 | Правила промпта формализованы | `05-prompt-assembly.md` + golden-тесты |
| K5 | Токены по слоям измерены | breakdown в TUI, CLI и отчёте |
| K6 | Очистка слоёв проверена | матрица 3×3, падают только свои вопросы |
| K7 | Полная модель отвечает ≥ 16/18 | прогон `stm+wm+ltm` |
| K8 | TUI и CLI работают | `./gradlew build test`, ручной чек-лист |
| K9 | Нет регрессий инструментов/токенов | unit-тесты Kotlin |

## Ограничения и допущения

- JVM 21, Gradle, один пользователь, одна активная беседа.
- TUI рассчитан на UTF-8 терминал ≥ 80×24; resize обрабатывается.
- Хранение — локальные JSON-файлы в data-dir; без сервера и БД.
- API — OpenAI-совместимый Chat Completions; ключ из env.
- По умолчанию извлечение кандидатов локальное (0 доп. запросов).
- LLM-извлечение опционально; при сбое откат на локальные правила.
- Retrieval LTM лексический (ключи, теги, слова), без embeddings.
- Реальный эксперимент требует ключа и ~150–200 запросов; автотесты — на
  fake-клиенте, без сети.
- Точные токены — из `usage`, иначе эвристика (кириллица дороже латиницы).
- День 10 остаётся рабочим; правки в нём — только опциональный экспорт facts.
