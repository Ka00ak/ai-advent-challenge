# 07. Методика проверки памяти

## 1. Гипотезы

| # | Гипотеза | Как проверяем |
|---|---|---|
| H1 | Каждый слой отвечает за свой класс вопросов | одиночные прогоны `stm`, `wm`, `ltm` |
| H2 | Слои не дублируют друг друга | очистка слоя ломает только его вопросы |
| H3 | Вместе слои покрывают то, что покрывает полная история | `stm+wm+ltm` ≥ 16/18 |
| H4 | Память дешевле полной истории | токены `stm+wm+ltm` < `full` |
| H5 | Вклад слоя измерим | `layerDelta` и инкремент между конфигурациями |

probe-вопрос добавляется сверху и не вытесняет их. Фазы A и B в STM
отсутствуют, поэтому их можно проверить только через LTM и WM.

**Почему сводка STM выключена в эксперименте**: сводка фазы B могла бы
«подсказать» ответы WM, а сводка фазы A — ответы LTM. Это смешало бы вклады
слоёв. Сводка проверяется отдельным тестом, не в ablation.

## 5. Конфигурации прогона

| ID | Слои | История | Назначение |
|---|---|---|---|
| `none` | — | только probe | нижняя граница |
| `stm` | STM | окно 8 | что даёт текущий диалог |
| `wm` | WM | — | что даёт рабочая память |
| `ltm` | LTM | — | что даёт долговременная память |
| `stm+wm` | STM + WM | окно 8 | диада |
| `stm+wm+ltm` | все | окно 8 | полная модель |
| `full` | — | все 34 | верхняя граница |

Общие настройки: `temperature = 0`, `maxTokens = 80`, `window = 8`
(8 сообщений истории + текущий probe), `summaryEnabled = false`,
`extractionMode = local`, `approval = confirm`.

## 6. Формулы токенов

Для каждой конфигурации фиксируются:

```text
system, ltmProfile, ltmRelevant, wm, stmSummary, stm, current, tools, total
```

`current` — текущая реплика probe; она одинакова во всех конфигурациях,
поэтому не влияет на дельты, но входит в `total`.

Прямой вклад слоя = сумма его блоков:

```text
LTM = ltmProfile + ltmRelevant
WM  = wm
STM = stmSummary + stm
```

Инкрементальная дельта (ablation):

```text
ΔLTM = total(stm+wm+ltm) − total(stm+wm)
ΔWM  = total(stm+wm)     − total(stm)
ΔSTM = total(stm)        − total(none)
```

Проверка: `ΔLTM ≈ LTM-блоки` с точностью до служебных токенов сообщений.
Расхождение больше 10 % — повод разобраться в сборке.

Экономия:

```text
saved = total(full) − total(stm+wm+ltm)
savedRatio = saved / total(full)
```

Если провайдер вернул `usage.prompt_tokens`, в отчёт идёт точное значение,
оценка — в отдельной колонке. Стоимость — по `estimateCost` Дня 10.

## 7. Прогон очистки

Стартовая точка — `stm+wm+ltm` с фикстурой.

| Шаг | Действие | Что ожидается |
|---|---|---|
| 1 | baseline | 18/18 (допуск ≥ 16) |
| 2 | очистить STM | падают S1–S6, остаются W и L |
| 3 | очистить WM | падают W1–W6, остаются S и L |
| 4 | очистить LTM | падают L1–L6, остаются S и W |

Правила очистки:

- STM: удалить сообщения и summary, сбросить `meta.processedMessages = 0`;
  WM, LTM, pending не меняются.
- WM: удалить пункты, `taskId = null`; STM, LTM, pending не меняются.
- LTM: удалить записи **и pending** (pending относится только к LTM);
  STM и WM не меняются. Ссылки `refLtmId` в WM становятся «потерянными».

Каждый шаг выполняется на копии baseline, а не поверх предыдущей очистки:
иначе нельзя отделить эффект слоёв.

## 8. Критерии успеха

| Проверка | Порог |
|---|---|
| `stm+wm+ltm` всего | ≥ 16 / 18 |
| каждый одиночный слой, свои вопросы | ≥ 5 / 6 |
| каждый одиночный слой, чужие вопросы | ≤ 1 / 6 |
| очистка слоя, его вопросы | ≤ 1 / 6 (то есть ≥ 5 сломались) |
| очистка слоя, чужие вопросы | ≥ 5 / 6 |
| `total(full) − total(stm+wm+ltm)` | > 0 |
| ΔLTM, ΔWM, ΔSTM | > 0 и согласуются с блоками ±10 % |
| секреты в слоях/аудите | 0 |

Если порог не выполнен, **нельзя подгонять фикстуру под результат**. Нужно
смотреть журнал промптов: какой блок не попал, какой retrieval отсёк запись,
какой кандидат не маршрутизировался. Выводы и причина фиксируются в отчёте.

## 9. Порядок выполнения

### Ручной прогон (реальный API)

1. `npm run dev -w 11`, указать base URL, модель и ключ.
2. «Память» → «Импортировать facts Дня 10» (если есть) или «Проверка» →
   «Загрузить фикстуру».
3. Проверить состав: STM 34 / окно 8, WM 7, LTM 15, pending 1.
4. «Проверка» → `quick` (9 вопросов: S1, S3, S5, W1, W3, W5, L1, L3, L5)
   для дымового теста.
5. «Проверка» → `full` (18 вопросов, 7 конфигураций = 126 запросов).
6. Включить «Проверка очистки» (+3 × 18 = 54 запроса, всего 180).
7. Скачать Markdown и JSON.
8. Сохранить как `docs/results/experiment-YYYY-MM-DD.md` и `.json`.
9. Заполнить выводы: что попало в слои, токены, что сломалось, совпало ли с
   гипотезами.

Ориентировочная стоимость на DeepSeek: 180 запросов × ~2 000 prompt-токенов ≈
$0.10–0.20. В `quick` — в 2 раза меньше.

### Автоматический прогон (Vitest)

```ts
// тест механики: мок отвечает "не знаю", если нужного блока нет в промпте
const answer = promptContains(probe.layer)
  ? probe.expected
  : 'не знаю'
```

Проверяется:

- в нужной конфигурации блок присутствует, в остальных — нет;
- счётчики `answered` совпадают с ожидаемой матрицей;
- очистка слоя убирает ровно его блок;
- токены считаются и дельта положительна;
- Markdown-отчёт содержит все таблицы.

Тест **не** проверяет качество модели: для этого нужен ручной прогон.

## 11. Интерпретация

| Наблюдение | Вывод |
|---|---|
| Слой отвечает на чужие вопросы | утечка данных между слоями или фикстурой; искать дубликаты |
| Свои вопросы падают при наличии слоя | retrieval/бюджет/рендер; смотреть `droppedLtmIds` и `notes` |
| Полная модель хуже `full` | потери при извлечении/усечении; это цена компактности, зафиксировать |
| Δ слоя отрицательна | ошибка измерения или блок не включён |
| Очистка ломает больше, чем свой слой | скрытая зависимость; описать и исправить |
| Модель отвечает «не знаю» на всё | нет ключа, неверная модель, пустой промпт |
