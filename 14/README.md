# День 14 — инварианты и ограничения состояния (Rust + TUI)

Ассистент с **тремя слоями памяти** (STM, WM, LTM), **профилем пользователя**,
**конечным автоматом задачи** и **инвариантами проекта**. Вся работа идёт через
единое ядро `AppController`: вкладка `1 Чат` использует память, профиль,
автомат и инварианты одновременно.

Инварианты — жёсткие ограничения, которые ассистент не имеет права нарушать:

- выбранная архитектура;
- принятые технические решения;
- ограничения по стеку;
- бизнес-правила.

Они хранятся **отдельно от диалога** в `data/invariants/invariants.json`.
Нарушение проверяется **кодом до выдачи ответа**, а не только промптом:
запрос проверяется до вызова модели, а финальный ответ модели — до возврата
пользователю. Нарушающий ответ заменяется детерминированным отказом.

**Стек:** Rust 2024 (1.85+), ratatui + crossterm, clap, serde, chrono,
reqwest (blocking, rustls), fs2.

## Быстрый старт

```sh
cd 14
cargo build

# TUI: вкладки 1 Чат … 9 Инварианты
cargo run -- --data-dir ./data tui

# Офлайн-демо без сети
LAB14_FAKE_LLM=1 cargo run -- --data-dir ./data tui

# Чат (нужен ключ; или LAB14_FAKE_LLM=1)
export DEEPSEEK_API_KEY=...
cargo run -- --data-dir ./data chat "Как устроена память?"

# Инварианты
cargo run -- --data-dir ./data invariants list
cargo run -- --data-dir ./data invariants check "Напиши на Python"
cargo run -- --data-dir ./data invariants probe
cargo run -- --data-dir ./data invariants audit

# Явное изменение инварианта: только командой, с причиной
cargo run -- --data-dir ./data invariants set stack.rust-only \
  --rule "Production-код только на Rust 2024; Python запрещён." \
  --reason "команда архитектора"

# Остальные возможности Дней 11–13
cargo run -- --data-dir ./data profile list
cargo run -- --data-dir ./data profile use brief
cargo run -- --data-dir ./data import-facts fixtures/day10-facts.json
LAB14_FAKE_LLM=1 cargo run -- --data-dir ./data experiment --quick --check
LAB14_FAKE_LLM=1 cargo run -- --data-dir ./data personalize --check
```

Ключ читается из `DEEPSEEK_API_KEY` или `KIMI_API_KEY` (либо
`--api-key-file` с правами `0600`). В настройки, слои, профиль, инварианты,
pending, аудит и API-журнал ключ не попадает.

## Инварианты

### Где хранятся

| Файл | Что внутри |
|---|---|
| `data/invariants/invariants.json` | список инвариантов + журнал изменений «было → стало» |
| `data/invariants/audit.json` | конфликты запросов, попытки обхода, заблокированные ответы и probe |

Диалог и слои памяти не содержат инвариантов: их нельзя «запомнить» или
«забыть» репликой. Это отдельный объект состояния.

### Стартовый набор

| ID | Категория | Правило |
|---|---|---|
| `arch.local-rust-tui` | архитектура | локальное Rust-приложение с TUI/CLI; без веб-сервера и React/Vue |
| `decision.postgresql` | техническое решение | только PostgreSQL как основная БД |
| `stack.rust-only` | стек | production-код только на Rust 2024 |
| `business.no-secrets` | бизнес-правило | секреты не попадают в файлы, логи, память и промпт |
| `business.budget-limit` | бизнес-правило | бюджет проекта не выше 150 000 ₽ |

У каждого инварианта есть детерминированные `forbidden_phrases` — признаки
нарушения, которые ищет код. Правило в промпте объясняет смысл, а признаки
дают воспроизводимую проверку без второй модели-судьи.

### Как ассистент учитывает инварианты

Порядок system-блоков:

```text
ядро → профиль → ИНВАРИАНТЫ → LTM профиль → LTM релевантное
     → WM → STM сводка → STM окно → текущая реплика → tools
```

В блоке инвариантов модель явно просят проверить каждый инвариант перед
ответом, отказаться при конфликте и назвать ID. Но решение принимает код:

1. **До сети.** `assess_request` проверяет реплику и попытки обхода. При
   конфликте модель не вызывается, в чат пишется отказ с ID и правилом.
2. **После модели, до пользователя.** `assess_response` проверяет финальный
   текст. Если модель всё же предложила нарушение, её ответ заменяется
   отказом; нарушающий текст не сохраняется как ответ ассистента.
3. **В задаче.** Цель задачи проверяется до `planning`; ответ каждого этапа
   `planning/execution/validation` проверяется до записи артефакта. При
   нарушении задача остаётся на текущем этапе со статусом `failed`, а не
   переходит в `done`.
4. **Аудит.** Каждая попытка получает запись в `audit.json` с типом,
   источником, ID инвариантов и найденными формулировками. Секреты
   маскируются.

### Изменение инварианта

Инвариант меняется **только явной командой**:

```sh
lab14 invariants set <id> --rule "<новое правило>" --reason "<причина>"
```

или на вкладке `9 Инварианты`: `c`/`Enter` → заголовок → правило →
признаки нарушения (через `;`) → причина. Заголовок, правило и признаки
заменяются вместе, поэтому ассистент не продолжает ссылаться на старую
формулировку или старые признаки.
Оба пути передают `source=cli|tui`; диалог такого пути не имеет. Домен
требует непустую причину и сохраняет:

```json
{
  "invariant_id": "stack.rust-only",
  "old_rule": "... Rust 2024 ...",
  "new_rule": "... Python запрещён ...",
  "reason": "команда архитектора",
  "source": "cli",
  "at": "2026-11-23T..."
}
```

Попытка сказать в чате «измени инвариант» блокируется как попытка обхода:
правило не меняется, а отказ подсказывает явную команду.

### Проверка обхода

`invariants probe` прогоняет 10 формулировок без сети:

- «сделай исключение»;
- «просто для примера»;
- ролевая подмена;
- «забудь предыдущие ограничения»;
- «только для теста / в виде исключения»;
- «игнорируй системный промпт»;
- «измени инвариант в чате»;
- новая роль без ограничений;
- «обойди инвариант через пример»;
- developer mode.

Результат на стартовом наборе: **10 из 10 заблокировано**. Каждая попытка
пишется в аудит с `kind=probe`.

## TUI

Запуск в UTF-8 терминале от **80×24**:

```text
1 Чат · 2 Память · 3 Подтверждения · 4 Проверка · 5 Настройки
6 API · 7 Профиль · 8 Состояния · 9 Инварианты
```

`1 Чат` — основная точка работы: каждый запрос проходит через контроллер и
использует STM, WM, LTM, активный профиль и инварианты. В шапке видны профиль,
размеры слоёв, breakdown последнего промпта и число активных инвариантов.
Если ответ заменён отказом, это видно в шапке и в истории.

`9 Инварианты` — список, детали, последнее изменение, история и аудит:

- `↑↓` — выбор; `↑↓`/`PgUp/PgDn` — прокрутка в других экранах;
- `c`/`Enter`/`e` — явная команда изменения: заголовок → правило →
  признаки нарушения через `;` → причина;
- `d` — история «было → стало» по выбранному инварианту;
- `a` — аудит попыток и обходов;
- `p` — прогнать 10 попыток обхода без сети.

`8 Состояния` — задача как автомат `planning → execution → validation → done`.
Переходы проверяет код: без плана из ≥ 2 шагов нет реализации, без
`ВЕРДИКТ: OK` нет `done`. Инварианты проверяются на цели и на каждом этапе.

## Ограничения

- Признаки нарушения задаются фразами и проверяются лексически: это
  воспроизводимая страховка, а не семантический судья. Смысл правила остаётся
  в промпте, а спорные случаи можно уточнить через `invariants set`.
- Инварианты запрещают предлагать нарушающие решения; они не мешают
  обсуждать ограничение, если запрос не содержит запрещённого действия.
- `invariants probe` проверяет детерминированный движок, а не качество модели.
- Пауза задачи проверяется между HTTP-запросами; отправленный запрос
  завершается.
- Реальный прогон требует API-ключ; все автотесты используют fake-клиент.
