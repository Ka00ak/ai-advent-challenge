# ai-advent-challenge-10 — 13.11.2026

Агент с **тремя стратегиями управления контекстом** и переключателем между ними:

- **Sliding Window** — в запрос уходят только последние N сообщений;
- **Sticky Facts** — отдельная key-value память `facts` + последние N сообщений;
- **Summary** — сводка старой части диалога + последние N сообщений (из Дня 9).

Все три стратегии прогоняются на одном контрольном диалоге из 24 сообщений и
12 деталей. После каждого прогона модель отвечает на 12 вопросов, а приложение
считает, сколько деталей она вспомнила, сколько токенов ушло и сколько
дополнительных запросов потребовала стратегия.

Плюс **ветвление диалога**: checkpoint, две независимые ветки от одной точки и
переключение между ними вместе с их собственной памятью.

Сделано на основе [09](../09): тот же агент с tool-calling, токенами, стоимостью,
localStorage и журналом API. Добавлены стратегии контекста, facts-память,
LLM-извлечение фактов, сравнительный benchmark на четыре режима и ветки.

Стек: **Vite 8 + Vue 3 + TypeScript**, OpenAI-совместимый Chat Completions API.
Тесты — Vitest.

## Стратегии

Выбор — «Настройки» → «Управление контекстом» → «Стратегия». Окно
`keepRecentMessages` (по умолчанию `8`) общее для всех трёх стратегий.

### 1. Sliding Window

```text
1. Взять последние N сообщений.
2. Выровнять границу по user-сообщению, чтобы не разорвать
   пару assistant(tool_calls) → tool.
3. Всё, что старше, не отправлять и не хранить в контексте запроса.
```

Полная история остаётся в `localStorage` для UI и экспорта, но модель её не
видит. Это самая дешёвая стратегия: **0 дополнительных запросов** и самый
маленький prompt. Плата — полная потеря деталей старше окна.

### 2. Sticky Facts / Key-Value Memory

Facts — это не пересказ, а таблица:

```json
{
  "facts": [
    {
      "key": "project.name",
      "value": "«Атлас»",
      "category": "имя",
      "updatedAt": "2026-11-15T12:00:00.000Z"
    },
    {
      "key": "budget.total",
      "value": "480 000 рублей",
      "category": "бюджет",
      "updatedAt": "2026-11-15T12:00:00.000Z"
    }
  ],
  "updatedAt": "2026-11-15T12:00:00.000Z",
  "processedMessages": 24,
  "updates": 9,
  "mode": "local"
}
```

Алгоритм:

```text
1. Найти сообщения, которые ещё не обработаны (processedMessages).
2. Для каждого user-сообщения извлечь факты и смержить по ключу.
   Одинаковый ключ перезаписывается: бюджет можно обновить без дубликата.
3. В запрос отправить: system-блок facts + последние N сообщений.
4. Полную историю и facts хранить раздельно.
```

Два режима извлечения:

| | `local` | `LLM` |
|---|---|---|
| Как | эвристика по шаблонам | отдельный запрос на каждое сообщение |
| Стоимость | 0 токенов | 1 запрос + prompt/completion на реплику |
| Что понимает | имена, сроки, бюджеты, ограничения, решения по шаблонам | свободные формулировки |
| Риск | пропустит нестандартную фразу | может ошибиться в JSON, есть fallback на local |

Промпт LLM-извлечения требует ключ на латинице (`project.deadline`,
`budget.total`, `decision.database`), дословное значение и категорию из
фиксированного списка. Если модель вернула не JSON, агент не падает: факты
извлекаются локально, а ошибка видна в статистике.

### 3. Summary

Стратегия из Дня 9: последние N сообщений как есть, более старая часть —
сводка. Обновляется порциями по `summarizeEveryMessages` (по умолчанию `10`).
Может работать через LLM или локальную выжимку. В модель уходит
`summary + последние N`.

## Сравнение стратегий

Контрольный диалог: **24 сообщения**, **12 деталей** в первых 16 сообщениях,
последние 8 — «шум» без фактов. Окно — 8 сообщений. Локальный расчёт без API
(эвристика токенов, поэтому цифры приблизительные):

| Стратегия | Деталей в контексте | Токенов в запросе | Экономия | Доп. запросы (local) | Доп. запросы (LLM) | Сложность кода |
|---|---:|---:|---:|---:|---:|---|
| Без стратегии (full) | 12 / 12 | 1 093 | — | 0 | 0 | — |
| Sliding Window | 0 / 12 | 331 | −70% | 0 | 0 | низкая, ~20 строк |
| Sticky Facts | 12 / 12 | 771 | −29% | 0 | 12 (по 1 на реплику) | средняя, ~220 строк + extractor |
| Summary (`local`) | 12 / 12 | 926 | −15% | 0 | 1 на порцию | высокая, ~300 строк + summarizer |

Что важно в этой таблице:

- **Sliding Window** выигрывает по токенам, но теряет все 12 деталей: они
  старше окна.
- **Sticky Facts** сохраняет все 12 деталей и при этом дешевле полной истории.
  В `local`-режиме не тратит запросы, в `LLM`-режиме платит за извлечение на
  каждой реплике.
- **Summary** сохраняет детали хуже, чем facts, если модель при пересказе
  пропустит число или имя. Зато даёт связный контекст, а не набор ключей.
- Чем больше окно, тем больше токенов у всех стратегий. Чем меньше окно, тем
  важнее качество facts/summary.

## Проверка памяти и benchmark

1. Открой вкладку «Стратегии».
2. Нажми **«Загрузить контрольный диалог»** — 24 сообщения, 12 деталей,
   facts строятся локально сразу.
3. Нажми **«Проверить все стратегии»**.
4. Приложение прогонит 4 режима × 12 вопросов = **48 запросов**:
   - full — полная история (baseline);
   - sliding — последние 8 сообщений;
   - facts — facts + последние 8;
   - summary — сводка + последние 8.
5. В таблице видно по каждой детали, вспомнил ли её каждый режим. В карточках —
   prompt-токены, токены на обновление памяти, число запросов и net-стоимость.

Ответ засчитывается по ключевым словам: «480 тыс. ₽» считается, необычная
формулировка без ключевого слова — нет. Это не семантическая оценка, зато
работает без дополнительной модели.

В LLM-режимах benchmark дополнительно тратит запросы:

- facts: по одному на каждое user-сообщение при построении памяти;
- summary: по одному на порцию старых сообщений.

Эти запросы видны в журнале API с бейджами `facts` и `summary`, а их токены
учтены в колонке «память» и в `net`.

## Ветвление диалога

1. Открой вкладку «Ветки».
2. Нажми **«Сохранить checkpoint»** — сохраняется снимок сообщений, сводки и
   facts в текущей точке.
3. Нажми **«Создать 2 ветки от checkpoint»** — появятся «Ветка A» и «Ветка B».
4. Продолжай диалог в активной ветке. У каждой ветки свои `messages`, свой
   summary и свои facts.
5. Переключайся кнопкой **«Переключиться»**. Интерфейс, история и память
   заменяются снимком выбранной ветки.

Ветки не делят массивы: сообщения и facts клонируются при создании. Продолжение
ветки A не меняет ветку B. Checkpoint остаётся общим и позволяет создать ещё
две ветки от той же точки.

## Где что хранится

Четыре независимых ключа `localStorage`:

```text
lab10.conversation.v1  → { version, id, createdAt, updatedAt, messages }
lab10.summary.v1       → { version, conversationId, text, coveredMessages, mode, chunks }
lab10.facts.v1         → { version, conversationId, facts, processedMessages, mode }
lab10.branches.v1      → { version, activeBranchId, checkpoint, branches }
```

Полная история никогда не удаляется из-за стратегии: sliding/facts/summary
влияют только на то, что уходит в запрос. При сбросе или импорте истории
summary, facts и ветки очищаются — старые индексы нельзя применять к другому
массиву сообщений.

## Токены и стоимость

Вкладка «Токены» показывает:

- полную историю;
- то, что реально уходит в запрос при выбранной стратегии;
- отдельно факты и сводку;
- экономию и процент;
- запросы на сжатие и извлечение facts с их стоимостью;
- рост prompt по шагам tool-loop.

Формула net-экономии для стратегии с памятью:

```text
net = full_history_tokens − (memory_tokens + tail_tokens) − memory_request_tokens
```

Для facts `memory_request_tokens` — это стоимость LLM-извлечения. В
`local`-режиме она равна нулю.

## Как устроено

```text
src/
  agent/
    Agent.ts          # tool-loop + выбор стратегии контекста
    context.ts        # sliding / facts / summary, preview и метрики
    facts.ts          # состояние facts, merge, локальное извлечение
    factExtractor.ts  # LLM-извлечение facts + парсинг JSON
    compression.ts    # summary: план, локальная выжимка, метрики
    summarizer.ts     # LLM-запрос на сводку
    history.ts        # починка незавершённых tool_calls
    ToolRegistry.ts   # схемы инструментов, вызов, обработка ошибок
  memory/
    dialog.ts         # контрольный диалог, 12 деталей, проверка совпадений
    benchmark.ts      # 4 режима × 12 вопросов, токены и стоимость
    branches.ts       # checkpoint, ветки, независимая память, localStorage
  storage/
    conversation.ts   # полная история
    summary.ts        # summary отдельным ключом
    facts.ts          # facts отдельным ключом
  components/
    SettingsPanel.vue # провайдер, стратегия, окно, факты, summary
    ContextPanel.vue  # стратегия, facts, summary, детали, benchmark, вывод
    BranchPanel.vue   # checkpoint, создание и переключение веток
    TokenPanel.vue    # контекст выбранной стратегии, память, стоимость
    HistoryPanel.vue  # история, ключи хранения, экспорт/импорт
    ApiLogPanel.vue   # журнал chat / summary / facts
  App.vue             # состояние, сохранение, запуск агента, benchmark, ветки
```

`Agent` не знает про localStorage. Он получает полную историю, summary, facts и
настройки стратегии, обновляет память, отправляет подготовленный контекст и
возвращает:

- полную историю с новыми сообщениями;
- актуальную сводку;
- актуальные facts;
- статистику стратегии и сжатия.

`App.vue` сохраняет историю, summary, facts и ветки раздельно.

## Ограничения

- Sliding Window по определению теряет всё старше окна. Это не баг, а цена
  дешевизны.
- Локальное извлечение facts работает по шаблонам и пропускает нестандартные
  формулировки. Для реальных диалогов нужен LLM-режим.
- LLM-извлечение facts — это запрос на каждую реплику; на длинном диалоге это
  дороже summary. Можно переключаться на `local` или батчить извлечение.
- Facts хранят только то, что попало в ключ-значение. Нюансы, шутки и
  промежуточные рассуждения теряются.
- Summary — пересказ, поэтому может потерять число или имя. LLM-сводка к тому
  же сама стоит токенов.
- Benchmark задаёт 48 запросов подряд, это заметно по времени и стоимости.
- Проверка памяти использует ключевые слова, а не семантику.
- Ветки хранят копии сообщений целиком: localStorage растёт вместе с числом
  веток. Для больших диалогов нужен переход на IndexedDB.
- Одна беседа и один набор памяти на браузер; журнал запросов живёт только в
  текущей сессии.
- Нет стриминга: ответ приходит целиком после каждого запроса.

## Вывод: какая стратегия для какого сценария

| Сценарий | Стратегия | Почему |
|---|---|---|
| Короткая сессия, поддержка, FAQ | **Sliding Window** | свежих сообщений достаточно, экономия максимальная, кода почти нет |
| Проектный диалог с фактами: сроки, бюджеты, имена, ограничения | **Sticky Facts** | детали не зависят от размера окна; в local-режиме бесплатно, в LLM — предсказуемо |
| Длинный свободный диалог, важны рассуждения и общий смысл | **Summary** | сохраняет связный контекст, а не только таблицу фактов |
| Нужен максимально дешёвый контекст и допустима потеря старого | **Sliding Window** | 0 дополнительных запросов и самый короткий prompt |
| Нужны и факты, и общий смысл | **Facts + Summary** (в разработке) | можно отправлять оба блока, но это дороже по токенам и коду |

Итог: **Sliding Window** — самая простая и дешёвая, **Sticky Facts** — самая
предсказуемая по деталям, **Summary** — самая гибкая по смыслу. Для проектного
диалога из 12 конкретных деталей facts выигрывают; для болтовни и длинных
рассуждений лучше summary; для экономии — окно.
