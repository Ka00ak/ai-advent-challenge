# 10. Архитектурные решения, риски, открытые вопросы

## ADR-1. Rust + TUI вместо веб-стека

**Контекст:** День 10 — Vue/TS. Требование Дня 11 — модель памяти; форма
интерфейса не задана, но нужна демонстрация и проверка.

**Решение:** отдельный Rust-проект с TUI (ratatui) и CLI (clap). Код Дня 10 не
переиспользуется, facts импортируются как данные.

**Следствия:** проще запуск и детерминизм, меньше зависимостей; нет браузера
и localStorage; нужна отдельная работа с файлами и терминалом.

## ADR-2. ratatui + crossterm

**Контекст:** нужен полноэкранный TUI с колонками, таблицами, модалками,
прогрессом и клавиатурой.

**Решение:** `ratatui` для отрисовки, `crossterm` для событий/terminal
backend. Никаких GUI-библиотек.

**Следствия:** зрелый стек, тестируемый через `TestBackend`; нужен аккуратный
event loop и восстановление терминала при панике. Мышь не обязательна.

## ADR-3. JSON-файлы вместо SQLite

**Контекст:** данные малы (сотни записей), нужна прозрачность и простой импорт.

**Решение:** отдельный JSON-файл на слой; атомарная запись, `.bak`, версия
схемы; `fs2` lock от двух экземпляров.

**Следствия:** файлы можно открыть и сравнить; нет транзакций между слоями
(каждый пишется отдельно); при росте данных — SQLite (P2).

## ADR-4. Блокирующий HTTP в worker-потоке

**Контекст:** TUI не должен зависать; эксперимент делает сотни запросов.

**Решение:** `reqwest::blocking` + отдельный `std::thread` на job; результаты —
через `mpsc` события. Без tokio/async.

**Следствия:** простой код и тесты; одновременно выполняется один job;
отмена — `AtomicBool` между запросами. Стриминг ответа не поддерживается.

## ADR-5. Один контроллер — TUI и CLI

**Контекст:** TUI сложно тестировать; агентам нужен headless-режим.

**Решение:** `AppController` содержит всю логику; TUI и clap-команды — тонкие
адаптеры. Все операции доступны в CLI.

**Следствия:** тесты и CI не зависят от терминала; TUI и CLI не расходятся;
CLI-вывод нужно форматировать отдельно.

## ADR-6. LTM по подтверждению

**Контекст:** требование «явно выбирать, что и куда сохраняется».

**Решение:** `Approval::Confirm` по умолчанию: WM пишется сразу, LTM — в
pending. `Auto` доступен, но не по умолчанию.

**Следствия:** контроль пользователя; очередь pending нужно хранить и
показывать; автоматический рост LTM ограничен.

## ADR-7. Лексический retrieval вместо embeddings

**Контекст:** векторный поиск требует модель/индекс/деньги.

**Решение:** score по key/tags/value + pinned + confidence + свежесть, top-K,
бюджет; детерминированно.

**Следствия:** синонимы могут не находиться; компенсируется тегами, pinned,
ручным поиском и LLM-извлечением. Embeddings — P2.

## ADR-8. Промпт собирается один раз за turn

**Контекст:** `memory_write` может вызваться в середине tool-loop.

**Решение:** блоки собираются перед первым запросом; tool-запись действует со
следующего хода.

**Следствия:** стабильный префикс, простая отладка; агент узнаёт о записи из
результата tool. Компромисс осознанный.

## ADR-9. Отдельное system-сообщение на блок

**Контекст:** можно склеить блоки в один system.

**Решение:** каждый блок — отдельное system; при несовместимости провайдера —
склейка в том же порядке с сохранением breakdown.

**Следствия:** прозрачный лог и токены по слоям; fallback для строгих API.

## ADR-10. Импорт facts из файла

**Контекст:** facts Дня 10 лежат в браузерном localStorage, недоступном Rust.

**Решение:** `import-facts <path>` читает `lab10.facts.v1`, `{"facts":[...]}` или
массив; sample `fixtures/day10-facts.json`; идемпотентный upsert.

**Следствия:** нужен экспорт из Дня 10 (кнопка/DevTools) или sample; старые
ключи не удаляются; миграция проверяема и воспроизводима.

## ADR-11. Эксперимент: детерминированная фикстура + keyword scoring

**Контекст:** нужны сравнимые результаты без второй модели-судьи.

**Решение:** 34 сообщения и 18 probe фиксированы; `temperature=0`; сводка STM
выключена в ablation; ответ оценивается по ключевым словам; fake-клиент для
тестов; реальный прогон — вручную/в CI с ключом.

**Следствия:** сравнимость; семантические синонимы могут не засчитаться; это
ограничение отмечено.

## ADR-12. WM хранится на диске

**Контекст:** задача может пережить перезапуск TUI.

**Решение:** `wm/working.json` с `task_id`; очистка/архив — вручную или GC.

**Следствия:** удобно; нужно следить за устареванием (`ttl_days`) и не путать
WM со STM.

## ADR-13. Ветки — удалены

**Контекст:** в Дне 10 ветки хранили messages+summary+facts; в Дне 11
планировался снимок всех слоёв.

**Решение:** по требованию заказчика функциональность веток исключена из
проекта: нет вкладки, branch-state и файла `branches/branches.json`.

**Следствия:** меньше кода и точек отказа; профиль и слои не откатываются
снимками.

## ADR-14. Ключ API только в окружении/0600

**Контекст:** ключ не должен попасть в память или репозиторий.

**Решение:** `DEEPSEEK_API_KEY`/`KIMI_API_KEY` или `--api-key-file` с правами
0600; в TUI показывается только источник и маска.

**Следствия:** удобно для CI; пользователь должен настроить env; ошибка
объясняется в TUI/CLI.

## Что считать провалом дня

- Три слоя только на бумаге, в промпт уходит один блок.
- Запись бесконтрольна, нет pending/аудита.
- Facts Дня 10 не импортированы.
- Нет измерения токенов по слоям.
- Очистка слоёв не проверена.
- Отчёт содержит выдуманные числа.
- TUI/CLI не запускаются или падают.
